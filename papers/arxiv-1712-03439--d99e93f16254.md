# Introduction

With advancements in deep learning , speech recognition accuracy has improved dramatically. Now, speech recognition systems are used not only on portable devices but also on standalone devices for far-field speech recognition. Examples include voice assistant systems such as Amazon Alexa and Google Home . In far-field speech recognition, the impact of noise and reverberation is much larger than near-field cases. Traditional approaches to far-field speech recognition include noise robust feature extraction algorithms , on-set enhancement algorithms , and multi-microphone approaches . Recently, we observed that training with large-scale noisy data generated by a _Room Simulator_ improves speech recognition accuracy dramatically. This system has been successfully employed for training acoustic models for Google Home or Google voice search .

_Room Simulator_ creates millions of virtual rooms with different dimensions and different number of sound sources at different locations and Signal-to-Noise Ratios (SNRs). For every new utterance in the training set, we use a randomly sampled room configuration, so that the same utterance is simulated under different acoustic environments in every epoch during training. As will be seen in Sec. <a href="#sec:experimental_results" data-reference-type="ref" data-reference="sec:experimental_results">3</a>, if we generate the simulated utterance only once for each input example, the performance is worse. Since different RIRs are applied for the same utterance at every epoch, the intermediate results cannot be cached. Therefore, the noisification process requires very large number of convolution operations. As will be seen in Sec. <a href="#sec:experimental_results" data-reference-type="ref" data-reference="sec:experimental_results">3</a>, during training, _Room Simulator_ used up to 80 % of the whole CPU usage if we use the CPU/GPU architecture shown in Fig. <a href="#fig:gpu_cpu_structure" data-reference-type="ref" data-reference="fig:gpu_cpu_structure">1</a>. In this paper, we describe our approach to reduce the computational portion of the _Room Simulator_ below 10 % of the CPU usage in our CPU/GPU training scheme.

# Efficient Implementation of the Room Simulation System

Fig. <a href="#fig:gpu_cpu_structure" data-reference-type="ref" data-reference="fig:gpu_cpu_structure">1</a> shows a high level block diagram of the acoustic model training infrastructure . Since it is not easy to run all the front-end processing blocks such as feature extraction and Voice Activity Detection (VAD) on GPUs, they run on CPUs during training. Even though Fast Fourier Transform (FFT) of the _Room Simulator_ may be efficiently implemented on GPUs, since _Room Simulator_ must feed the simulated utterances to the rest of CPU optimized front-end components, the Room Simulator is also running on CPUs.

In this section, we briefly review the structure of the Google Room Simulator for generating simulated utterances to train acoustic models for speech recognition systems . We assume a room of a rectangular cuboid-shape as shown in Fig. <a href="#fig:room_diagram" data-reference-type="ref" data-reference="fig:room_diagram">2</a>. Assuming that all the walls of a room reflect acoustically uniformly, we use the image method to model the Room Impulse Responses (RIRs) . In the image method, a real room is acoustically mirrored with respect to each wall, which results in grids of virtual rooms. In our work for training the acoustic model for Google Home , we consider $`17 \times 17 \times 17 = 4913`$ virtual rooms for RIR calculation. Following the image method and assuming that there are $`V`$ virtual sound sources including one real source, the impulse response is calculated using the following equation :

```math
\begin{align}
    h[n] = \sum_{v = 0}^{V-1} \frac{r^{g_v}}{d_v}
    \delta \left[n -\left \lceil{\frac{d_v f_s}{c_0}}\right \rceil \right],
      \label{eq:h_n_calculation}
\end{align}
```

where $`v`$ is the index of each virtual sound source, and $`d_v > 0`$ is the distance from that sound source to the microphone, $`0 < r < 1`$ is the reflection coefficient of the wall, $`g_v`$ is the number of the reflections to that sound source, $`f_s`$ is the sampling rate of the RIR, and $`c_0`$ is the speed of sound in the air. We use the value of $`f_s = 16,000`$ _Hz_ and $`c_0 = 343`$ _m/s_ for _Room Simulator_ . For $`d_v`$, $`r`$, we use numbers created by a random number generator following specified distributions for each impulse response .

Assuming that there are $`I`$ sound sources including one target source and $`J`$ microphones, the received signal at microphone $`j`$ is given by:

```math
\begin{align}
  y_j[n] =  \sum_{i=0}^{I-1} \alpha_{ij} \left(h_{ij}[n] * x_i[n]\right).
  \label{eq:y_j_def}
\end{align}
```

Since we used a two-microphones system in $`J`$ is two, and for the number of noise sources, we used a value from zero up to three with an average of 1.55. Including the target source, the average number of $`I`$ is 2.55 .

## Efficient Room Impulse Response filtering

When the signal and the room impulse response lengths are $`N_x`$ and $`N_h`$ respectively, the number of multiplications $`C_{td}`$ required for calculating <a href="#eq:y_j_def" data-reference-type="eqref" data-reference="eq:y_j_def">[eq:y_j_def]</a> using the time-domain convolution is given by:

```math
\begin{align}
  C_{td} = I \times J \times N_x \times N_h.
  \label{eq:num_mults_linear_convolution}
\end{align}
```

In our training set used in , the average utterance length including _non-speech_ portions marked by the Voice Activity Detector (VAD) is 7.31 _s_. This corresponds to $`N_x`$ of 116,991 at 16 _kHz_. The average length of the RIR in the room simulator used in is 0.243 _s_, corresponding to the $`N_h`$ value of 3893. For Google Home the number of noise sources in our training set is 1.55 on average. Thus $`I`$ is 2.55 including one target source, and $`J`$ is two, since we use a two-microphones system in . Thus, if we directly use the linear convolution, it requires 2.32 billion multiplications per utterance from <a href="#eq:num_mults_linear_convolution" data-reference-type="eqref" data-reference="eq:num_mults_linear_convolution">[eq:num*mults_linear_convolution]</a>, which is prohibitively large. Thus, in the “\_Room Simulator*" in , we used the frequency domain multiplication using `Kiss FFT` . To avoid time aliasing, the FFT size $`N`$ must satisfy $`N \ge N_x + M - 1`$, where $`M`$ is the length of the impulse response. The $`j`$-th microphone channel of the simulated signal $`y_j[n]`$ in <a href="#eq:y_j_def" data-reference-type="eqref" data-reference="eq:y_j_def">[eq:y_j_def]</a> is given by:

```math
\begin{align}
  y_{j} [n] = \sum_{i=0}^{I-1}FFT^{-1} \left \{
      FFT \left \{ h_{ij}[n] \right \} \times
      FFT \left \{ x_i[n] \right \}
      \right \}.  %* FFT\{X_i[omega_k}\}\}
  \label{eq:fir_fft_convolution}
\end{align}
```

As shown in <a href="#eq:fir_fft_convolution" data-reference-type="eqref" data-reference="eq:fir_fft_convolution">[eq:fir*fft_convolution]</a>, we perform two FFTs, one IFFT, and one complex element-wise multiplications between two complex spectra for each convolution term in <a href="#eq:y_j_def" data-reference-type="eqref" data-reference="eq:y_j_def">[eq:y_j_def]</a>. Assuming that radix-2 FFTs are employed, each FFT or IFFT requires $`\frac{N}{2} \log_2(N)`$ multiplications . In addition, a single element-wise complex multiplication between two complex spectra is required for each convolution term in <a href="#eq:y_j_def" data-reference-type="eqref" data-reference="eq:y_j_def">[eq:y_j_def]</a>. For real time-domain signals, we need to perform element-wise multiplications for the lower half-spectrum for Discrete Fourier Transform (DFT) indices $`0 \le k \le N / 2`$ since the spectrum has the Hermitian symmetry property . From this discussion, we conclude that the number of real multiplications $`C*{\textit{FFT}}`$ for calculating <a href="#eq:fir_fft_convolution" data-reference-type="eqref" data-reference="eq:fir_fft_convolution">[eq:fir_fft_convolution]</a> is given by:

```math
\begin{align}
  C_{\textit{FFT}} = I J \left(6 N \log_2(N) + 2 N\right).
  \label{eq:c_fft}
\end{align}
```

For the average $`N_x`$ of 116,991 mentioned above, if we assume that the average $`N`$ is $`2 ^ {17}`$, <a href="#eq:c_fft" data-reference-type="eqref" data-reference="eq:c_fft">[eq:c*fft]</a> requires 69.5 million multiplications per utterance on average. \_Room Simulator* for was implemented in C++ using the `Eigen3` linear algebra library . So far we have used the `Kiss FFT` version of FFT in `Eigen3` including acoustic model training for Google Home described in . But, to further speed up frontend computation, we switched from `Kiss FFT` in `Eigen3` to a custom C++ class implementation which internally uses real FFT in `FFTW3`.

A more efficient approach is using the OverLap Add (OLA) FFT filtering . With the OLA FFT filtering, the approximate number of real multiplications is given by:

```math
\begin{align}
  C_{\textit{OLA}} = I J \left(
          \left \lfloor{\frac{N_x}{N - N_h + 1}}\right \rfloor
          \left(4 N \log_2(N) + 2 N  \right)   \right.  \nonumber \\
           \left.
                   \vphantom{\left \lfloor{\frac{N_x}{N - M + 1}}\right \rfloor}
            + 2 N \log_2(N) \right),
  \label{eq:c_ola}
\end{align}
```

where $`N`$ is the FFT size, $`N_x`$ is the length of the entire signal, and $`N_h`$ is the length of the impulse response. The term $`4 N \log_2(N) + 2 N`$ appears in <a href="#eq:c_ola" data-reference-type="eqref" data-reference="eq:c_ola">[eq:c*ola]</a>, since there is one FFT, one IFFT, and one element-wise complex multiplication for $`0 \le k \le N / 2`$ for each block. As before, we assumed that each FFT or IFFT requires $`\frac{N}{2} \log_2(N)`$ multiplications and one complex multiplication requires four real multiplications in <a href="#eq:c_ola" data-reference-type="eqref" data-reference="eq:c_ola">[eq:c_ola]</a>. $`\left \lfloor{\frac{N_x}{N - M + 1}}\right \rfloor`$ is the number of blocks to process an utterance of length $`N_x`$. The $`2 N \log_2(N)`$ term in <a href="#eq:c_ola" data-reference-type="eqref" data-reference="eq:c_ola">[eq:c_ola]</a> is required for FFT of the impulse response $`h*{ij}[n]`$. For the impulse response $`h*{ij}[n]`$, we do not need to repeat it for every block. In our training set consisting of 22 million utterances mentioned above, the average $`N`$ is 116,991 and the average $`N_h`$ is 3,893. For this average $`N`$ and $`N_h`$, the minimum value of $`C*{\textit{OLA}}`$ in <a href="#eq:c_ola" data-reference-type="eqref" data-reference="eq:c_ola">[eq:c_ola]</a> is 50.8 millions of real multiplications when $`N = 2^{14}`$. The optimal value of $`N`$ minimizing $`C*{\textit{OLA}}`$ is different for different $`N_h`$ and $`N_x`$ values. For each filtering, we minimize $`C*{\textit{OLA}}`$ by evaluating this equation with different values of $`N = 2^{m}`$ where $`m`$ is an integer.

## Room Impulse Response Length Selection

The average length of the Room Impulse Response in the original room simulator is estimated to be 3893 samples, which corresponds to 0.243 _s_. We perform a simple RIR tail-cutoff by finding the RIR power threshold which is $`\eta`$ _dB_ below the maximum power of the RIR $`h_{ij}[n]`$:

```math
\begin{align}
  p_{th} = \max \left \{h_{ij}^2[n] \right \} \times 10^{-\frac{\eta}{10}}.
  \label{eq:p_th_def}
\end{align}
```

Using $`p_{th}`$, we find the cut-off index $`n_c`$ which is the smallest sample index beyond which all the trailing $`h_{ij}[n]`$ has power below the threshold $`p_{th}`$:

```math
\begin{align}
  n_c = \min_{m} \left\{
  m \middle| \max_{n > m} \left\{  h^2[n] \right \} <  p_{th}  \right \}.
\end{align}
```

Then the final RIR cut-off $`\widehat{h}_{ij}[n]`$ is given by the following equation:

```math
\begin{align}
  \widehat{h}_{ij}[n] = h_{ij}[n], \qquad 0 \le n \le n_c + 1.
\end{align}
```

Fig. <a href="#fig:rir_cutoff" data-reference-type="ref" data-reference="fig:rir_cutoff">3</a> shows the original impulse responses and the corresponding RIR when the cutoff threshold of $`\eta`$ is used. To reflect the typical case in our training set, we used the average room dimension, average microphone-to-target distance, and average $`T_{60}`$ value among 3 million room configurations described in .

As shown in Table <a href="#tbl:local_machine_prof" data-reference-type="ref" data-reference="tbl:local_machine_prof">6</a> and <a href="#tbl:cpu_percentage" data-reference-type="ref" data-reference="tbl:cpu_percentage">[tbl:cpu*percentage]</a>, the RIR tail cut-off at 20 \_dB* shows relatively 35.6 % to 69.4 % speed improvement on a local desktop machine and on `Google Borg` cluster . Fig. <a href="#fig:rir_cutoff_local_profiling" data-reference-type="ref" data-reference="fig:rir_cutoff_local_profiling">4</a> shows the profiling results on a local machine with different RIR cutoff thresholds $`\eta`$. The local machine we used has a single `Intel(R) Xeon(R) E5-1650 @ 3.20GHz` CPU with 6 cores and 32 GB of memory. In Fig. <a href="#fig:rir_cutoff_local_profiling" data-reference-type="ref" data-reference="fig:rir_cutoff_local_profiling">4</a>, we observe that the computational cost becomes less for the OLA filtering case as we cut the tail portion of the RIR more. For the full FFT case, theoretically, it should remain almost constant regardless of the impulse response length, but due to variation in profiling measurement, there is some small variation.

# Experimental results

In this section, we present speech recognition results and CPU profiling results obtained using _Room Simulator_ with different RIR cut-off thresholds. The acoustic modeling structure to obtain experimental results in this section is somewhat different from those described in for faster training. We use a single-channel 128 log-Mel feature whose window size is 32 _ms_. The interval between successive frame is 10 _ms_. The low and upper cutoff frequencies of the Mel filterbank are 125 _Hz_ and 7500 _Hz_ respectively. Since it has been shown that long-duration features represented by overlapping features are helpful , four frames are stacked together. Thus we use a context dependent feature consisting of 512 elements given by 128 (the size of the log-mel feature) x 4 (number of stacked frames). This input is down-sampled by a factor of three . The feature is processed by a typical multi-layer Long Short-Term Memory (LSTM) acoustic model. We use 5-layer LSTMs with 768 units in each layer. The output of the final LSTM layer is passed to a softmax layer. The softmax layer has 8192 nodes corresponding to the number of tied context-dependent phones in our ASR system. The output state label is delayed by five frames, since it was observed that the information about future frames improves the prediction of the current frame . The acoustic model was trained using the Cross-Entropy (CE) loss as the objective function, using precomputed alignments for utterance as targets. To obtain results in Table <a href="#tbl:results" data-reference-type="ref" data-reference="tbl:results">[tbl:results]</a>, we trained for about 45 epochs.

For training, we used an anonymized and hand-transcribed 22-million English utterances (18,000-hr) set. The training set is the same as what we used in . For evaluation, we used around 15-hour of utterances (13,795 utterances) obtained from anonymized mobile voice search data. We also generate noisy evaluation sets from this relatively clean voice search data. We use both simulated and rerecorded noisy sets. The average reverberation time in $`T_{60}`$ of the simulated training set and two simulated test sets are shown in Table <a href="#tbl:avg_t_60" data-reference-type="ref" data-reference="tbl:avg_t_60">11</a>. These two simulated test sets are named _Simulated Noisy Set A_ and _Simulated Noisy Set B_ respectively.

Since our objective is deploying our speech recognition systems on far-field standalone devices such as Google Home, we rerecorded these evaluation sets using the actual hardware in far-field environment. Note that the actual Google Home hardware has two microphones with microphone spacing of 7.1 cm. In our experiments in this section, we selected the first channel out of two channel data. Three different devices were used in rerecording, and each device was placed in five different locations in an actual room resembling a real living room. These devices are listed in Table <a href="#tbl:results" data-reference-type="ref" data-reference="tbl:results">[tbl:results]</a> as “Device 1”, “Device 2”, and “Device 3”. As shown in Table <a href="#tbl:results" data-reference-type="ref" data-reference="tbl:results">[tbl:results]</a>, we observe that the RIR cut-off up to 20 _dB_ threshold does not adversely affect the performance. However, if we cut the RIR to 5 _dB_ threshold, then the performance under far-field environment becomes significantly worse. This observation also confirms that far-field speech recognition benefits from RIRs with sufficiently long tails in the training set. Table <a href="#tbl:cpu_percentage" data-reference-type="ref" data-reference="tbl:cpu_percentage">[tbl:cpu*percentage]</a> shows how much CPU resource was used when training is done on `Google Borg` cluster using the CPU/GPU training architecture in Fig. <a href="#fig:gpu_cpu_structure" data-reference-type="ref" data-reference="fig:gpu_cpu_structure">1</a>. We observe that if we use the `FFTW3`-based OLA filter using 20 \_dB* RIR cutoff, we may obtain 57.6 times speed-up in the FFT portion. The entire speed-up of _Room Simulator_ portion is 37.3 times.

# Conclusions

In this paper, we describe how to efficiently implement an acoustic room simulator to generate large-scale simulated data for training deep neural networks. We implement an efficient OverLap Addition (OLA) based filtering using the open-source `FFTW3` library. We investigate into the effects of the Room Impulse Response (RIR) lengths. We conclude that we can cut the tail portions of RIRs whose power is less than 20 _dB_ below the maximum power without sacrificing speech recognition accuracy. However, if we cut off RIR more than that, we observe it adversely affects the performance for reverberant cases. Using the approaches mentioned here, we could reduce the room simulator portion in the CPU usage down to 9.69 % in CPU/GPU training architecture. Profiling result shows that we obtain 22.4 times speed-up on a local desktop machine and 37.3 times speed up on `Google Borg` cluster.
